# prd-to-html 설계 문서

- 날짜: 2026-08-18
- 상태: 승인 대기 (브레인스토밍 완료, 사용자 설계 승인 완료)

## 1. 목적

`PRD.md`를 **사람이 읽기 위한 단일 HTML 문서**로 변환하는 `/prd-to-html` 커맨드.

핵심 문제 인식: prd-maker의 `PRD.md`는 AI 코딩 에이전트를 위한 지침으로 설계됐다. 그러나 프로젝트 오너도 같은 문서를 이해해야 한다 — 무엇을 만드는지, 무엇을 안 만드는지, 어떤 `(가정)`을 자기가 확인해줘야 하는지. 마크다운 원문은 이 역할에 실패한다. 수용 기준 체크박스와 페이즈 요구사항이 평평한 텍스트로 나열되면 오너는 읽지 않고, 읽어도 자기가 결정해야 할 것이 무엇인지 못 찾는다.

이 커맨드는 그 문서를 다시 쓰지 않는다. **같은 사실을 사람이 읽는 순서로 재배치한 뷰**를 만든다.

## 2. 확정된 요구사항

| 항목 | 결정 |
|---|---|
| 렌더링 주체 | 결정적 파이썬 스크립트 (LLM 생성 아님) |
| 입력 범위 | 관대함 — PRD 7섹션 구조면 완전한 뷰, 아니면 읽기 좋은 기본 뷰로 자동 격하 |
| prd-maker 연결 | PRD 완성 후 **제안**만 (자동 생성 아님) |
| 인터랙션 | 정적 문서 + 최소 JS (검색은 브라우저 Ctrl+F에 위임, 상태 저장 없음) |
| 산출물 | 단일 self-contained HTML (외부 리소스 0) |
| 다이어그램 | 없음 (CSS 타임라인으로 대체) |
| 의존성 | stdlib 전용 (저장소 기존 정책 유지) |

### 지배 원칙 두 개

1. **파생 뷰(derived view)다.** HTML은 원문에 없는 사실을 만들지 않는다. 일정·비용·지표·사용자 플로우를 "보기 좋으라고" 생성하는 순간 prd-maker의 `(가정)` 규율이 무너지고 스킬 전체의 신뢰가 무너진다. 결정적 스크립트를 택한 첫 번째 이유가 이것이다 — 원칙을 프롬프트 준수가 아니라 코드 구조로 강제한다.
2. **원본이 SSOT다.** HTML은 언제든 버리고 재생성할 수 있는 산출물이며, 그 사실을 문서 자신이 푸터에 명시한다. HTML에 상태를 저장하지 않는 이유도 같다.

## 3. 아키텍처

```
prd-maker/
├── commands/
│   ├── prd-maker.md
│   └── prd-to-html.md              # [신규] /prd-to-html → 스크립트 직접 실행
└── skills/
    └── prd-maker/
        ├── references/
        │   └── quality-rules.md    # [수정] 전달 메시지에 HTML 뷰 제안 추가
        └── scripts/
            ├── validate_prd.py     # 파서 자산 제공 (변경 없음)
            ├── prd_to_html.py      # [신규] 변환기
            └── test_prd_to_html.py # [신규] 유닛 테스트
```

새 스킬을 만들지 않는다. 변환이 완전히 결정적이라 LLM 판단이 개입할 지점이 없고, SKILL.md를 추가하면 빈 껍데기가 되며 `check_skill_structure.py`의 단일 스킬 경로 가정도 깨진다. 커맨드는 스크립트를 실행하고 결과 경로를 안내하는 역할만 한다.

### `prd_to_html.py` 내부 구역

한 파일에 담되 네 구역을 명확히 나눈다. 지금 파일로 쪼개면 서로만 호출하는 모듈 4개가 생겨 얻는 것이 없다.

| 구역 | 단일 책임 | 의존 |
|---|---|---|
| 파서 | md → 구조 데이터(섹션·페이즈·요구사항·수용기준·가정) | `validate_prd` |
| 미니 마크다운 렌더러 | 인라인/블록 문법 → 이스케이프된 HTML 조각 | 없음 |
| 템플릿 | 구조 데이터 → 단일 HTML 문자열 (CSS·JS 인라인) | 위 둘 |
| CLI | 인자 처리, 파일 입출력, 오류 보고 | 전부 |

### 파서 자산 재사용

`validate_prd.py`에서 `strip_fenced_blocks`, `NUMBERED_SECTION_RE`, `PHASE_RE`, `CHECKBOX_RE`, `NUMBERED_ITEM_RE`, `ASSUMPTION_RE`, `find_section_body`를 import한다. 정규식을 두 벌 두지 않는 것이 핵심 — 린터가 "가정"이라 부르는 것과 HTML이 "가정"이라 부르는 것은 영원히 같아야 한다. 이 계약은 테스트 3번이 지킨다.

### 임계값 없는 부분 강화

"7섹션이면 완전한 뷰, 아니면 폴백"이라는 분기를 두지 않는다. **각 강화 요소는 자기 데이터가 존재할 때만 렌더된다.** `## 4.`가 있으면 Non-Goals 블록이 나타나고, 없으면 사라진다. 결과적으로 임의의 마크다운은 저절로 읽기 좋은 기본 뷰로 떨어지므로 폴백 코드 경로가 따로 없고, 사용자가 PRD를 손으로 편집해 섹션 하나를 지워도 문서가 갑자기 다른 종류로 바뀌지 않는다.

### 마크다운 렌더링 범위

Python stdlib에 마크다운 파서가 없고 이 저장소는 의존성이 0이다. 플러그인 사용자에게 `pip install`을 요구하면 마찰이 커지므로, PRD가 실제로 사용하는 부분집합만 처리하는 렌더러를 직접 작성한다.

지원: `#`~`###` 제목, 순서/비순서 목록, 체크박스 항목, `**볼드**`, `` `인라인 코드` ``, 인용 블록, 파이프 표, 펜스 코드 블록, 링크.
미지원 문법은 원문 그대로 이스케이프해 출력한다 — 깨지지 않고 못생길 뿐이다.

목록 중첩은 지원하지 않는다. 들여쓴 하위 항목은 같은 목록의 형제로 평탄화된다. PRD 템플릿은 중첩 목록을 쓰지 않고, 들여쓰기 상태를 추적하려면 블록 렌더러가 눈에 띄게 복잡해지는 데 비해 얻는 것이 없다. 폴백 경로로 들어온 임의 마크다운에서는 계층이 한 단계 납작해지지만, 내용이 사라지지는 않는다.

원문의 raw HTML은 렌더하지 않고 전부 이스케이프한다. PRD 템플릿이 pure markdown을 요구하므로 표현 손실이 없고, 신뢰할 수 없는 마크다운을 변환해도 안전하다.

## 4. 출력 문서 구성

오너 레인과 에이전트 레인을 별도 페이지로 쪼개지 않고 **읽는 순서로 층을 쌓는다.** 위쪽일수록 오너, 아래쪽일수록 구현자.

| 층 | 내용 | 주 독자 |
|---|---|---|
| 1. 헤더 | 제품명, 원본 파일명, 생성 시각, 원본 `.md` 상대 링크 | 공통 |
| 2. 요약 대시보드 | 페이즈 수 · 요구사항 수 · 수용기준 수 · Non-Goals 수 · **가정 수**. 각 숫자는 해당 섹션 앵커 | 오너 (5초 글랜스) |
| 3. `(가정)` 검토 패널 | 가정 항목 전체 목록 + 원문 위치 앵커 | 오너 (액션 아이템) |
| 4. 본문 | 원문 섹션 순서 그대로. §3 기능은 카드, §4 Non-Goals는 강조 블록, §5는 `[변경 금지]` 배지, §6은 CSS 타임라인 + 페이즈 카드 | 공통 |
| 5. 요구사항 인덱스 표 | ID / 페이즈 / 요구사항 / 수용기준 수 | 엔지니어·에이전트 |
| 6. 푸터 | 파생물 고지 ("수정은 `PRD.md`에서") | 공통 |

3층이 이 도구의 존재 이유에 가장 가깝다. prd-maker는 전달 메시지에서 사용자에게 `(가정)` 확인을 요청하지만, 그 목록은 대화가 끝나면 사라진다. HTML은 그 목록을 문서 안에 상주시킨다.

### ID와 앵커

- 요구사항: `P1-R3` → `#p1-r3`
- 수용 기준: `P1-A2` → `#p1-a2`

슬랙에 링크를 붙여넣거나 에이전트에게 "P2-R4 바꿔줘"라고 지시할 수 있게 하는 것이 마크다운 원문 대비 실질적인 이득이다. 페이즈 구조가 없는 문서에서는 ID를 부여하지 않는다.

### 다이어그램을 넣지 않는 이유

mermaid 런타임은 수 MB 규모라 인라인하면 자족성이 파일 크기로 무너지고, CDN 참조는 오프라인·사내망에서 깨진다. 페이즈 흐름은 CSS 타임라인으로 충분히 표현되며, 그 이상인 사용자 플로우 다이어그램은 **원문에 없는 사실**이므로 결정적 변환기가 만들어서는 안 된다.

## 5. 스타일 사양

| 항목 | 값 |
|---|---|
| 본문 | 60ch 내외 · 16–17px · line-height 1.7 |
| 한글 | `word-break: keep-all` + `overflow-wrap: anywhere` |
| 폰트 | 시스템 폰트 스택만, 웹폰트 0 |
| 목차 | ≥1024px 좌측 sticky + 스크롤스파이, 이하 상단 `<details>` |
| 본문 접기 | 없음 |
| 다크모드 | `prefers-color-scheme` + 수동 토글, 라이트가 기본 |
| 배지 | 색 + 텍스트 라벨 + 문자 아이콘 병기 |
| 인쇄 | `break-inside: avoid`(표·카드·코드), 링크 URL 노출, 목차·토글 숨김, 강제 흑백 |
| JS | 스크롤스파이 + 다크 토글, 인라인 30줄 내외 |

`lang` 속성은 한글 문자 비율로 `ko`/`en`을 추정해 넣는다 — 스크린리더 발음이 달라진다.

본문을 접지 않는 것은 미학이 아니라 기능적 결정이다. 개발자는 문서를 열자마자 Ctrl+F를 누르는데, 접힌 콘텐츠는 브라우저 검색에 걸리지 않는다. 목차는 본문이 아닌 내비게이션이므로 좁은 화면에서 접어도 무방하다.

## 6. 파일 정책과 오류 처리

- 기본 출력: 입력과 같은 디렉터리의 `<입력 파일명>.html` (`PRD.md` → `PRD.html`)
- `--output <경로>`로 변경 가능
- **덮어쓰기 허용.** 원본 `PRD.md`와 달리 이것은 언제든 재생성 가능한 파생물이다. 사용자가 HTML을 직접 편집하는 것은 지원 대상이 아니며 푸터가 이를 명시한다
- 종료 코드: 0 성공 / 2 사용 오류(인자 누락, 파일 없음, UTF-8 아님). `validate_prd.py`의 관례를 따른다
- 입력이 비어 있거나 제목이 하나도 없어도 실패하지 않는다 — 최소 뷰를 생성한다

## 7. 검증

`skills/prd-maker/scripts/test_prd_to_html.py` (stdlib 전용, 기존 테스트 스타일):

| # | 검증 | 막는 회귀 |
|---|---|---|
| 1 | `docs/examples/*.md` 변환 후 `html.parser`로 well-formed | 렌더러 문법 오류 |
| 2 | 출력에 `<script src=` / `<link href=` / `@import` / 외부 URL 리소스가 0개 | 자족성 상실 |
| 3 | HTML 가정 패널 항목 수 == `validate_prd.py` ASSUMPTIONS 수 | 린터-변환기 파서 드리프트 |
| 4 | `<script>`가 든 마크다운 입력 → 실행 가능한 스크립트 없음 | 이스케이프 누락 |
| 5 | 섹션 번호 없는 임의 마크다운 → 예외 없이 변환, 대시보드만 사라짐 | 부분 강화 파손 |
| 6 | 출력에 `@media print`와 `prefers-color-scheme` 존재 | 인쇄·다크 스타일 유실 |

CI는 `.github/workflows/ci.yml`의 `linter-tests` 잡에 스텝 하나, `scripts/check-all.sh`에 한 줄을 추가한다.

## 8. prd-maker 연결

`references/quality-rules.md`의 "Delivery message requirements"에 항목 5를 추가한다: PRD 저장 후 사용자에게 HTML 뷰 생성을 **제안**하고, 사용자가 동의하면 `prd_to_html.py`를 실행한다.

`SKILL.md`는 수정하지 않는다. 150줄 CI 캡이 걸려 있고, 전달 메시지 규칙은 이미 `quality-rules.md`가 소유하고 있다.

자동 생성을 택하지 않은 이유: 원본과 파생물이 항상 함께 저장소에 남으면 둘 중 어느 쪽이 진실인지 흐려진다. 사용자가 명시적으로 요청할 때만 만들어야 파생물이라는 지위가 유지된다.

## 9. 범위 밖 (v1)

- 사용자 플로우·아키텍처 다이어그램 생성 (원문에 없는 사실)
- 자체 검색창, 필터, 진행률 저장 (Ctrl+F와 SSOT 원칙)
- 테마 커스터마이즈, 사용자 CSS 주입
- PDF 직접 생성 (브라우저 인쇄로 충분)
- 임의 마크다운의 섹션 의미 휴리스틱 추론 (문서 언어가 사용자마다 다름)

## 10. 리서치 근거

| 설계 결정 | 근거 |
|---|---|
| 본문 접기 금지 | 개발자는 문서를 열자마자 Ctrl+F를 누르며, 접힌 콘텐츠는 브라우저 검색에 걸리지 않는다. NN/g도 "여러 섹션을 동시에 봐야 하면 전부 펼쳐 보여라"고 명시 |
| 요약 대시보드 최상단 | 비기술 이해관계자는 5초 글랜스 테스트로 문서를 판단한다. 사람은 20년째 F-패턴으로 스캔한다 (NN/g) |
| 오너/에이전트 층 분리 | 목적이 다른 문서 유형을 섞으면 양쪽 독자가 모두 실패한다 (Diátaxis). 현재 `PRD.md`는 reference인데 오너는 explanation을 필요로 한다 |
| Non-Goals를 강조 블록으로 | 엔지니어가 실제로 읽는 것은 문제·경계·수용 기준·의존성이며, 특히 명시적 스코프 경계를 읽는다 |
| 요구사항 ID 부여 | 요구사항 추적 관례(RTM)에서 ID는 참조와 검증의 단위다 |
| 60ch·16px·1.7 | 본문 45–75자 권장, 기술 문서는 하한이 유리. 본문 최소 16px |
| `word-break: keep-all`, 행간 155%+ | 한글 웹 타이포그래피 관행 (KRDS 등) |
| 라이트 모드 기본 | 장문 가독성은 positive polarity가 우위 |
| 색 + 라벨 병기 | 색만으로 의미를 전달하면 색각 이상 사용자에게 정보가 사라진다 (WCAG) |
| 인쇄 CSS 필수 | 이해관계자에게는 결국 PDF로 전달된다. 표·카드는 `break-inside: avoid` 없이 페이지 경계에서 깨진다 |
| 외부 CDN 금지 | 오프라인·사내망에서 문서가 깨진다 |
